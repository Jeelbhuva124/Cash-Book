1. SYSTEM ARCHITECTURE & COMPONENT FLOW DIAGRAM
================================================================================
File Name: system_architecture_diagram.jpg

[A] PURPOSE & OVERVIEW:
This diagram illustrates the complete 3-Tier Client-Server Architecture of the
Cash-Book platform. It highlights how the independent User Dashboard and
Admin Portal interfaces interact with the backend Express.js REST API and
Socket.IO layer to read and write data to the central MongoDB database.

[B] KEY MODULES & LAYERS:
1. Top Layer - Admin Portal:
   - Admin Dashboard: Live platform telemetry, overall stats, revenue counters.
   - User Management & Status Control: RBAC, account activation/suspension.
   - Global Cashbook Management: Multi-tenant audit and storage monitoring.
   - Audit & Transaction Logs: Master ledger stream and soft-delete recovery.
   - System Analytics: Traffic, active users count, growth metrics.

2. Middle Layer - Database Core (MongoDB):
   - Central normalized database holding collections: User, Admin, Cashbook,
     Transaction, Invitation, Category, PaymentMode, EmiSubscription.
   - Indexed queries on user_id, chalan_id, and date for ultra-fast response.

3. Bottom Layer - User Dashboard:
   - User Authentication: Secure login, JWT token issuance, session control.
   - Multi-Cashbook Management: Create separate books with custom color codes.
   - Income & Expense Engine: Ledger recording with categories & payment modes.
   - Party Ledger (Khata): Debtor/Creditor tracking with automated interest.
   - EMI & Subscription Vault: Recurring liability scheduler & due date alerts.
   - Collaborative Sharing: Real-time book access with role permissions.
   - Reports & Analytics: Dynamic charts and 1-click vector PDF generation.

[C] VIVA PRESENTATION PITCH (What to say to the examiner):
"Sir, this diagram illustrates our 3-tier decoupled MERN architecture. The
presentation layer is cleanly divided into a User Dashboard and an Admin Portal.
Both communicate with an Express.js server via REST endpoints and Socket.IO,
maintaining complete data isolation and transactional integrity across our
MongoDB collections."

2. DATABASE ENTITY-RELATIONSHIP (ER) SCHEMA DIAGRAM
================================================================================
File Name: database_er_diagram.jpg

[A] PURPOSE & OVERVIEW:
The Entity-Relationship (ER) Diagram establishes the logical database design,
primary keys (PK), foreign keys (FK), attributes, and cardinality (1-to-Many
relationships) governing cashbook ledgers, multi-user sharing, and audit trails.

[B] KEY ENTITIES & RELATIONSHIPS:
1. User Table (user_info collection):
   - PK: id
   - Attributes: name, email, role, phone_number, security_pin, account_status.
   - Relation: 1 User owns Many Cashbooks (1:N).

2. Cashbook Table (cashbooks collection):
   - PK: id
   - FK: user_id (links to User)
   - Attributes: cashbook_name, hex_code, description, cashbook_type.
   - Relations:
     * 1 Cashbook owns Many Transactions (1:N) via chalan_id.
     * 1 Cashbook issues Many Invitations (1:N).
     * 1 Cashbook tracks Many EmiSubscriptions (1:N).

3. Transaction Table (transactions collection):
   - PK: id
   - FK: chalan_id (links to Cashbook id)
   - Attributes: title, amount, type (income/expense), date, time, category,
     subcategory, payment_mode, remark, party_type, party_name, interest_rate,
     is_deleted (used for soft-delete pattern).

4. Invitation Table (invite_info collection):
   - PK: id
   - Attributes: email, invite_name, inviter_email, cashbook_name,
     permissions (Viewer, Editor, Admin), status (Pending, Accepted, Rejected).

5. EmiSubscription Table (emi_subscriptions collection):
   - PK: id
   - FK: chalan_id
   - Attributes: title, amount, due_date, start_date, end_date, status, type.

6. Admin Table (admins collection):
   - PK: id
   - Attributes: username, email_id, password, user_role, account_status.

[C] VIVA PRESENTATION PITCH:
"Sir, our ER diagram represents a normalized MongoDB schema. The core anchor
entity is the Cashbook. Through the foreign key chalan_id, transactions,
invitations, and EMI schedules remain strictly bound to an individual ledger,
preventing cross-tenant data contamination."

3. USER JOURNEY PROCESS FLOW DIAGRAM
================================================================================
File Name: user_process_flow.jpg

[A] PURPOSE & OVERVIEW:
This diagram depicts the complete end-to-end user experience, from sign-up to
daily transaction recording, debt management, collaborative sharing, and report
generation.

[B] STEP-BY-STEP WORKFLOW:
- Step 1: User Onboarding & Security
  * Registration via Email or Google Auth.
  * Setup of a 4-Digit Quick Security PIN for fast authorizations.
  * Active Sessions review to view and terminate suspicious device logins.

- Step 2: Multi-Cashbook Setup
  * Creation of purpose-specific cashbooks (e.g., Personal, Shop, Event).
  * Color badge customization for instant visual distinction.
  * Instant switching between cashbooks from the dashboard header.

- Step 3: Transaction Entry (Income / Expense)
  * Selecting +Cash In or -Cash Out.
  * Entry of amount, date, category (e.g., Salary, Groceries, Rent).
  * Selection of payment method (Cash, UPI, Card, NetBanking).
  * Attachment of receipts or invoices via the Receipt Vault.

- Step 4: Special Business Modules
  * Party Ledger (Khata): Managing Debtors (Lena hai) & Creditors (Dena hai)
    with interest calculation.
  * EMI & Subscription Tracker: Due date countdowns and automated alerts.

- Step 5: Collaboration via Invitations
  * Sending an email invite to a partner or family member.
  * Selecting access level: Viewer (read-only), Editor (can add), or Admin.
  * Real-time ledger synchronization via Socket.IO upon acceptance.

- Step 6: Visual Analytics & PDF Statement Export
  * Reviewing interactive charts (Income vs Expense breakdown).
  * 1-Click download of professional PDF balance sheets using jsPDF.

[C] VIVA PRESENTATION PITCH:
"Sir, the User Process Flow demonstrates our user-centric design. A user can
manage multiple distinct books, record receipts with transactions, track debts
with interest, collaborate in real time, and download official PDF statements."

4. ADMIN WORKFLOW DIAGRAM
================================================================================
File Name: admin_process_flow.jpg

[A] PURPOSE & OVERVIEW:
This diagram details the administrative control flow for platform governance,
user moderation, compliance auditing, and disaster recovery.

[B] STEP-BY-STEP WORKFLOW:
- Step 1: Admin Authentication & RBAC Guard
  * Secure Admin Login portal (/admin/login).
  * Cryptographic token verification enforcing is_admin === true.
  * Frontend route protection via AdminProtectedRoute.

- Step 2: Dashboard Overview & System Telemetry
  * Live monitoring of platform statistics: Total Registered Users,
    Active Cashbooks count, Gross Transaction Volume, and Server Load.

- Step 3: User Governance & Moderation
  * Searching and filtering the global user directory.
  * Account status toggle between Active and Suspended for policy violations.
  * Facilitating PIN and password recovery requests.

- Step 4: Cashbook Supervision
  * High-level inspection of all active cashbooks across all organizations.
  * Anomaly detection for unusual transaction spikes.
  * Cashbook lock and archival capabilities.

- Step 5: Master Transaction Oversight & Soft-Delete Recovery
  * Continuous audit trail of all platform ledger entries.
  * Soft-Delete Recovery: If a user deletes an entry by mistake, the admin
    can locate the is_deleted: true record and restore it with one click.

- Step 6: Administration & Delegation
  * Super-Admin capabilities to invite and onboard sub-administrators.
  * Role delegation and global platform preference configuration.

[C] VIVA PRESENTATION PITCH:
"Sir, the Admin Workflow ensures regulatory compliance and security. The admin
monitors system health and moderates users without invading private data, and
can recover accidentally deleted records using our soft-delete architecture."

5. DATA FLOW DIAGRAM LEVEL 0 (CONTEXT LEVEL DFD)
================================================================================
File Name: dfd_level_0.jpg

[A] PURPOSE & OVERVIEW:
The Context-Level DFD establishes the software boundary. It treats the entire
platform as a single central process bubble (0.0 Cash-Book Management System)
and maps all external entities exchanging data with the system.

[B] ENTITIES & DATA EXCHANGES:
1. User (Primary External Entity):
   * Inputs to System: Credentials, Cashbook settings, Transaction inputs,
     Party Khata records, EMI schedules.
   * Outputs from System: Balance alerts, dynamic analytics, PDF statements.

2. Collaborator / Partner (Secondary Entity):
   * Inputs to System: Invitation acceptance/rejection, shared entries.
   * Outputs from System: Shared cashbook data and live balance feeds.

3. Admin / Auditor (Supervisory Entity):
   * Inputs to System: System commands, user suspension, role updates.
   * Outputs from System: Audit logs, user metrics, platform telemetry.

4. External Services (Email & WebSockets):
   * Outbound notification delivery (Nodemailer) and live push broadcasts
     (Socket.IO).

5. Central Data Store:
   * D1: MongoDB Database (holding all system states).

[C] VIVA PRESENTATION PITCH:
"Sir, Context Level DFD (Level 0) represents the black-box view of Cash-Book. It
shows how our central system arbitrates data between Users, Collaborators,
Admins, and External Notification services."

6. DATA FLOW DIAGRAM LEVEL 1 (DFD LEVEL 1)
================================================================================
File Name: dfd_level_1.jpg

[A] PURPOSE & OVERVIEW:
DFD Level 1 decomposes the central bubble 0.0 into 8 distinct sub-processes and
5 specialized data stores, detailing exactly how internal data flows between
functional modules and collections.

[B] DECOMPOSED SUB-PROCESSES:
- Process 1.0 (User Authentication): Validates credentials, issues JWT tokens,
  and manages PIN security (Reads/Writes D1: User Store).
- Process 2.0 (Cashbook Management): Creates and configures cashbooks, tags
  colors, and updates cashbook metadata (Reads/Writes D2: Cashbook Store).
- Process 3.0 (Transaction Processing): Receives Income/Expense inputs, tags
  categories, and computes updated balances (Reads/Writes D3: Transaction Store).
- Process 4.0 (Party Ledger & Interest): Tracks debtor/creditor debts and
  calculates accumulated interest (Reads/Writes D3: Transaction Store).
- Process 5.0 (EMI & Due Reminders): Monitors due dates against system clocks
  and fires alert notifications (Reads/Writes D5: EMI Store).
- Process 6.0 (Collaboration & Invites): Dispatches book sharing invites and
  verifies permission claims (Reads/Writes D4: Invitation Store).
- Process 7.0 (Report Generation): Extracts transaction history from D2 and D3
  to render visual charts and vector PDF files.
- Process 8.0 (Admin System Audit): Queries data across D1 through D5 to
  compile system analytics and perform soft-delete transaction recovery.

[C] DATA STORES MAPPING:
- D1: User Store (user_info)
- D2: Cashbook Store (cashbooks)
- D3: Transaction Store (transactions)
- D4: Invitation Store (invite_info)
- D5: EMI Store (emi_subscriptions)

[D] VIVA PRESENTATION PITCH:
"Sir, DFD Level 1 exposes the inner workings of our software. It partitions the
system into 8 discrete sub-processes interacting with 5 isolated data stores.
This modularity ensures that high-volume transaction writes do not bottleneck
user authentication or report generation."
